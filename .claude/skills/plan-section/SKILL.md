# Plan Section

Generate or update a section spec for grantmahn.com. The spec is the contract between the planner, builder, and evaluator — it defines what should be built and how it should be judged.

The user provides a section name as an argument (e.g., `hero`, `work`, `services`, `about`, `contact`, `footer`, `suit-spec`, `fitting-room`).

## Workflow

1. **Read brand context.** Read `CLAUDE.md` at the project root. Internalize the color system, typography scale, page structure, tailoring metaphor, and AI Slop Test.

2. **Explore the codebase.** Find the existing implementation for this section:
   - Search `src/app/page.tsx` for the section's markup (look for the section ID or class)
   - Search `src/app/globals.css` for the section's styles
   - Check `src/animations/` for any related animation files
   - Note what exists, what's missing, and what's broken

3. **Check for existing spec.** Read `docs/section-specs/{name}.md` if it exists.
   - If it exists: compare the spec against the current implementation. Propose updates to bring the spec in line with reality, or flag where the implementation has drifted from the spec.
   - If it doesn't exist: generate a new spec from scratch.

4. **Write the spec.** Follow this template structure exactly:

```markdown
# Section Spec: {NAME}

> Generated by /plan-section. Review and edit before building.

## Product Context
- **Job:** What this section must accomplish for the visitor (one sentence)
- **Content Hierarchy:** Numbered list of elements in priority order
- **Emotional Arc Position:** Where this section sits in the visitor's journey
- **Tailoring Metaphor:** How the tailoring theme manifests here

## Design Direction
- **Fabric Texture:** Which pattern, implementation method, opacity
- **Background Layers:** Back-to-front stacking order
- **Animations:** Entrance behavior, timing, easing
- **Typography:** Font, size, weight, spacing for each element

## Success Criteria
1. (numbered, testable, specific)

## Anti-Patterns
1. (numbered, specific things NOT to do)

## Do Not Touch
- (elements that must not be modified)

## Dependencies
- (what this section relies on)
```

5. **Save the spec** to `docs/section-specs/{name}.md`.

6. **Present for review.** Show the spec to the user. Highlight any decisions that need their input. The user reviews and edits before the builder touches any code.

## Key Principles

- The spec is the user's vision, not Claude's. Propose, don't dictate.
- Every Success Criterion must be testable — "looks good" is not a criterion.
- Anti-Patterns should reference specific failure modes from the AI Slop Test.
- The Do Not Touch list inherits from CLAUDE.md but can add section-specific items.
- If the section already exists in code, the spec should describe the INTENDED state, not just document what's there. Gaps between spec and implementation are the builder's work.
